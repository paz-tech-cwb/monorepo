## Major
- [M1] mobile/Android, navigation [`FormulariosViewModel.kt` `onFormTap`, `FormulariosScreen.kt` NavigateToSubmissionsList]. The catalog now returns `can_read=true` for a leader or co-leader (it was already true for `life_group_leader`/area/sector). `onFormTap` sends any form with `canRead` to `Screen.FormSubmissionsList`, and that screen loads `getServiceReportSubmissions()` (the service-report list). So on Android, tapping "Relatório de Life Group" in Formulários shows service reports, never the new submit screen. The `FormSteps` and `FormDetail` redirects in `PazNavGraph` only fire when the effect is `NavigateToForm`, which does not happen for readers. The docs (`mobile-app.md`) and the commit claim the Formulários list is an entry point. Only the group-detail row ("Enviar relatório") and search/deep link reach the screen. iOS is fine: it always routes to `FormDestinationView`. Fix: in `FormulariosScreen`'s `NavigateToSubmissionsList` branch (or in `onFormTap`), route `FormType.life_group_report` to `Screen.LifeGroupReportSubmit.createRoute()`, same as the existing `casa_de_paz_report` special case. Add a ViewModel or screen test.

## Minor
- [m1] backend, `life-group-report-create-policy.ts` order. 404 for an unknown group and 403 for an existing but forbidden group let any authenticated user probe which group ids exist. The spec already orders 403 before 422 to avoid leaking sector/area info. Group ids are sequential and not sensitive, so this is acceptable. Optional hardening: 404 for both cases, as `findEntity` does for out-of-scope reports.
- [m2] backend, PATCH `life-group-reports.service.ts` `update`. The future-date check only runs on create. A submitter can PATCH `date` into the future (within 24h of creating). Reuse `assertDateNotInFuture(dto.date)` when `dto.date` is present. Low impact: the reminder week math assumes dates are not in the future.
- [m3] backend, reminder `form-report-reminder.evaluator.ts`. A report counts for "this week" by meeting `date` >= Monday. A leader who reports on Monday for last Sunday's meeting (date < Monday) is still nagged on Sunday. Acceptable for the Sunday-evening default; worth a doc line (the docs mention only the Monday boundary). Also, `submitted_by` only: a co-leader's submission does not silence the leader (documented).
- [m4] mobile, admin/pastor with no led groups cannot submit from mobile (picker lists only leader/co_leader groups, documented), even though the backend allows it. Product choice, matches spec; no change needed.
- [m5] admin-ui, `life-group-reports-form.tsx`. The form still has area/sector pickers whose values are ignored by the backend (documented). It also doesn't check the comma-split caps client-side. `splitList` silently truncates to 20 items and 80 chars, whereas mobile shows an error. Harmless, but the area/sector pickers can mislead admins; consider removing them in a follow-up.
- [m6] tests: the policy and controller specs mock the EntityManager, so the real TypeORM `findOne` with `relations` plus nested `select` (leader, coLeader, sector.area) is not exercised against a database. I traced the entity relations (`sector.area` exists) and TypeORM 0.3.26 supports nested select; low risk, but worth one manual QA POST on a real DB.

## Verified (no issues)
- Policy order and rules: date (400, Sao Paulo day via `zonedParts`, compared on the first 10 chars so full ISO strings work), group exists (404), access (admin/pastor via `unrestricted`, scope `lifeGroupIds` including supervisors, or leader/co-leader fallback; else 403), then 422 for missing sector/area. area_id/sector_id are always derived; the DTO accepts and ignores them.
- Removing `@Roles`/`RolesGuard` on POST only: no other route is widened (GET/PATCH/DELETE unchanged; the `ScopeGuard` and `AuthGuard` remain). A plain member now reaches the policy and gets 403/404.
- Global pipe is `whitelist + forbidNonWhitelisted + excludeExtraneousValues`, so old clients sending `area_id`/`sector_id` on POST or `life_group_id`/area/sector on PATCH are silently ignored, not rejected. `OmitType` keeps the `@Expose` names and validators of the remaining fields (controller spec exercises PATCH with the real pipe). PATCH for legitimate edits still works and cannot move a report between groups.
- DTO caps match the DB (`numeric(10,2)` pattern, varchar(180), counts 0..100000, arrays 20x80). Mobile (`LifeGroupReportRules`) and admin-ui use the same limits.
- Catalog: `leadsLifeGroup` flag only on `life-group-reports` (no widening of other forms, tested); one `EXISTS` query per catalog call and only for non-privileged actors. `leader_id`/`co_leader_id` are FK columns on a small table; acceptable. (Postgres does not auto-index FKs; add an index only if the table grows large.)
- Reminder skip: query is `DISTINCT s.id` over non-deleted reports (entity QB applies `deleted_at IS NULL`), `date >= Monday` in Sao Paulo (ISO Monday via `(weekday+6)%7`), only for the `life-group-reports` slug, other slugs unchanged; the early return when everyone reported prevents an empty notification.
- admin-ui: payload arrays, `offering` regex, Sao Paulo default date, types (`LifeGroupReport` arrays, `LifeGroupReportPayload`), detail view joins arrays with the existing generic `Array.isArray` branch and gains labels. `tsc` reports no errors in touched files (other files have pre-existing errors).
- Android: imports resolve (`ReportsSkeleton`/`ReportsMessage` are `internal` in the same package; `PickerField` is public; `PazSuccessState`/`PazErrorState`/`PazButton` signatures match; `Icons.AutoMirrored.Outlined.Assignment` imported in `MinistryDetailScreen`). Koin `viewModel { (lifeGroupId: Int?) -> ... }` with `parametersOf(lifeGroupId?.toIntOrNull())` follows the existing analytics pattern. `if (x) { { Text() } } else null` composable-lambda patterns are valid. `SelectableDates`/`DatePicker` usage is correct (UTC millis; minSdk 26 so `java.time` is fine). Optional-arg route `life_group_report_submit?lifeGroupId={lifeGroupId}` has a nullable `StringType` argument with `defaultValue = null`. The ViewModel test follows the `MainDispatcherRule` + `runTest` pattern used by sibling tests.
- Shared: `LifeGroupReportForm` serial names match the DTO exactly (`offering` string, arrays, optional `*_other`, no area/sector); no leftover wrong-payload path (generic `FormDetailViewModel`/`FormDetailViewModelIOS` branches now refuse to post and the field defs are empty). Error mapping covers 400/403/404/409/422/429/5xx/network. The group picker uses `/life-groups/me` and only `leader|co_leader`.
- iOS: pbxproj hand edit is consistent (6 new ids, each unique, fileRef/build file/group/Sources phase for 2 app files and the test target file). View model logic mirrors Android via the shared draft; `FormDestinationView` is used by the list, search and deep link. iOS was built and tested per `test-results.md` (53 tests).
- PR #96: no code conflict (see above); only pipeline docs conflict and are trivially resolvable.
- Docs: accurate except the "Formulários list" entry-point claim for Android (see M1). `forms.md`, `life-groups.md`, `notifications.md` match the implementation.
