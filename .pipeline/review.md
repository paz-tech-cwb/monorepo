## PR #102 (backend)

### Blockers / Major
- none.

### Minor
- [b1] `life-group-analytics.service.ts` `overview()`: when `life_group_id` is supplied and the caller is unrestricted but the id does not exist, the 404 is raised only after `groupsRaw` is fetched (fine), but a RESTRICTED caller with a non-existent or foreign id gets 403 `life_group_access_forbidden` (no existence oracle: good, intended). Note the two cases return different codes for unrestricted vs restricted callers; clients map both fine.
- [b2] `OverviewQueryDto` now makes `/overview` strict under `GLOBAL_VALIDATION_PIPE_OPTIONS` (`forbidNonWhitelisted: true`): any unknown query param now returns 400 (before: ignored, there was no DTO). Checked callers: admin-ui has NO overview caller (`admin-ui/lib/api/endpoints/life-group-analytics.ts` only attendance/distribution); mobile (`LifeGroupAnalyticsRepositoryImpl.kt:53`, previous builds too) sends no params, new build sends only `life_group_id`. No regression found. Worth a line in the release notes.
- [b3] Response now includes `life_group_id` (null when unscoped); mobile Json has `ignoreUnknownKeys = true`, so old builds are safe. Scoped response has `members_total === members_in_group` by design (documented in code).

### Verified
- `codedErrorBody` shape (`statusCode,error,code,message`) matches what the meetings API sent inline; the `error` title-casing of `HttpStatus` keys is correct (e.g. NOT_FOUND -> "Not Found"). Codes added: `group_not_found` (attendance + meetings + overview), `life_group_access_forbidden` (access util + analytics resolve), `invalid_meeting_date_format|invalid_meeting_date|date_in_future`, `invalid_extra_meeting_param`. Messages are unchanged text, so any consumer matching `message` keeps working; adding `code` to legacy attendance endpoints is backward compatible.
- Authorization of `overview?life_group_id=`: goes through the same `resolveLifeGroupIds` as attendance/distribution: unrestricted -> `[id]`; restricted -> must be in `scope.lifeGroupIds` or led/co-led by actor (`lg.leader_id|co_leader_id = actor.id`), else 403; supervisors/area/sector leaders via `scope.lifeGroupIds`. Group, member and kids queries are all restricted to that single id, the users query is `lg.id = :id` and bypasses the sector branch only after authorization, so no data from other groups leaks; `life_groups` dropdown list contains only that group when scoped.
- Backend tests: unit specs for analytics/attendance/meetings pass (200 tests); eslint clean on changed dirs; integration specs not run here (DB required).

### Verdict #102: SHIP (APPROVE).
