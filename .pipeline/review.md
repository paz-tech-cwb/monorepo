## Major
- [M1] State / UX - `android/.../lifegroupmeeting/LifeGroupMeetingHistoryScreen.kt:79-88` + `LifeGroupMeetingHistoryViewModel.kt:35-46`. The ViewModel loads in `init` (`load(showSkeleton = true)`); the `LifecycleEventObserver` is registered while the owner is already RESUMED, so it immediately dispatches ON_RESUME -> `refresh()` -> `load(showSkeleton = false)`, which sets `isLoading = false, isRefreshing = true` while `meetings` is still empty. Result: on EVERY first open the user sees the "Nenhuma reunião registrada ainda" empty state (not the skeleton) until the network answers, the three requests run twice, and the two in-flight loads race (older response can overwrite newer). Fix: make `refresh()` a no-op while a load is in flight (`if (_uiState.value.isLoading) return`), and/or `isLoading = showSkeleton || it.meetings.isEmpty()` (what the iOS VM already does: `showSkeleton: meetings.isEmpty`); keep a `Job` and cancel the previous one. Add a VM test: init + refresh must never expose `isLoading=false && meetings.isEmpty()` before the first response.
- [M2] Perf / correctness of default date - `LifeGroupMeetingHistoryViewModel.kt:52`. To learn `meetingDay` it calls `churchRepository.getAllLifeGroups()` (whole list, `GET /api/life-groups`, role-scoped, unbounded for admin/pastor) on every load AND every resume/pull-to-refresh, then `find`s one group. If the caller cannot see the group in that list (co-leader whose role is `member`, scoped listing) `meetingDay` stays null: the "Nova reunião" default silently becomes today and the "reunião extra" hint never shows (server still enforces, so no data bug). iOS does it right (receives `meetingDay` from the detail screen). Fix: pass `meetingDay` as a nav/Koin argument from `LifeGroupDetailScreen` (it already holds `group.meetingDay`), or use `GET /life-groups/:id`; at minimum fetch the group once (not on refresh).
- [M3] Data integrity (product) - `LifeGroupMeetingUiState.kt:63-67`, `LifeGroupMeetingReportDraft.validate/toInput` (`LifeGroupMeeting.kt:132-207`). A never-touched report form validates (blank = 0) and `canSaveReport` is true for a new report (`!isReportSaved`), so one accidental tap on "Salvar relatório" files an all-zero report with offering 0.00. A report existing silences the reminder follow-up and counts as "Relatório enviado" in history. Fix: require at least one field touched (e.g. `reportDirty` for the first save, i.e. `canSaveReport = canEditReport && !isBusy && reportDirty`), or a confirm dialog when everything is blank. Same on iOS (`LifeGroupMeetingViewModel.canSaveReport`).
- [M4] Merge-readiness with PR #97 - see section below: 2 textual conflicts (MinistryDetailScreen.kt, pbxproj) plus a product-level overlap (two report entry points). Must be resolved by whoever merges second; not a defect of this PR alone.

## Minor
- [m1] Lost in-flight edits - `LifeGroupMeetingViewModel.kt:163-190, 228-237`: `onTogglePresent`/`onReportChanged` are not blocked while a save is in flight (only the Switch/fields are disabled in the UI, rows are not: `MemberRow enabled = !readOnly`, `Screen.kt:209`). On success `entries`/`reportDraft` are overwritten from the response, dropping toggles made during the request. Disable `MemberRow` when `isBusy` (UI) and guard `onTogglePresent/onAllPresentChanged` with `isBusy` (VM). Same shape on iOS.
- [m2] Draft write on leaving - `persistDraft()` (`ViewModel.kt:270-291`) launches in `viewModelScope`; if the user taps back right after a keystroke, `onCleared` cancels the job and the last edit may not reach DataStore. Wrap the write in `withContext(NonCancellable)` (small, bounded write) or use an app-scoped scope.
- [m3] Stale draft overlays newer server data silently apart from the banner (`applyLoaded`, `ViewModel.kt:103-120`): if the co-leader saved the report from another device, the restored local report draft replaces it in the form and a save overwrites theirs. Acceptable for v1; consider dropping the report draft when `meeting.report` exists and was updated after the draft (needs a timestamp in the draft) or showing "dados mais novos no servidor".
- [m4] `load()` after a stale draft with `extraMeeting=true` whose group changed to "Sem dia fixo"/the date became regular -> 400 `extra_meeting_not_applicable|extra_meeting_on_regular_day` is shown as a load error and every retry re-reads the same draft (loop, `ViewModel.kt:54`). On those two codes, clear the stored draft's `extraMeeting` and refetch without the flag.
- [m5] `LifeGroupMeetingRules.normalizeOffering` (`LifeGroupMeetingRules.kt:133-137`): "0.125" (leading zero whole part, 3 decimals) is read as thousands separator -> "125.00" (money silently x1000). Require `whole.first() != '0'` for the thousands interpretation (else return null). Add a test.
- [m6] Route with invalid arguments renders a blank destination (`PazNavGraph.kt:259-289`, `return@composable`): a malformed push leaves an empty screen with a back stack entry. Prefer `LaunchedEffect { navController.popBackStack() }` or an error state. Same for the 400 "future date" message which shows backend English text (`byStatus 400` uses `serverMessage`).
- [m7] Logout clears drafts only through `AuthRepositoryImpl.logout` (`AuthRepositoryImpl.kt:92-93`). Confirmed: Android `AccountViewModel:75`, `EditProfileViewModel:218` and iOS `IosAppContainer.logout:123` all go through it, and keys are per-user so a forced teardown cannot leak across accounts. Optional: also `clearAll()` in `login()` next to `formsRepository.clearCache()` so a forced teardown path never leaves another user's drafts at rest.
- [m8] History merge only knows report dates + saved attendance; a legacy report on a non-regular date with no attendance appears as "Presença pendente" and opens a screen where attendance cannot be saved (`attendance == null`) and the report shows "Salve a presença para liberar o relatório." (`UiState.kt:76`) - misleading; show a read-only legacy message when `meeting.attendance == null && meeting.report != null`.
- [m9] UX: "Todos presentes" OFF marks everyone absent (`setAllPresent(false)`), which also fires automatically-looking state because the switch flips off as soon as one member is unchecked (checked = `allPresent`). Flipping it off again by tapping wipes all presence. Consider an action button/tri-state instead of a switch. Author-flagged; fine to ship.
- [m10] History screen: `navController.navigate(...)` from a collected effect plus `onMeetingTapped` going through a Channel is fine, but on ON_RESUME refresh the whole list recomposes with `isRefreshing`; no regression, just noting M1 is the only issue there.
- [m11] Tests: Android VM tests are good (extra flow, order attendance->report, window close during save, user-scoped drafts, 409 mapping) but nothing covers M1/M2 or "edit while saving". `FakeMeetingDraftStore` exists twice (android test util, shared commonTest) - fine (different modules).
- [m12] `Character.isNumber`/`isDigit` filters (iOS `ReportSection.swift:130`, Android `CountField`) accept non-ASCII digits; shared `parseCount` rejects them so the user gets a validation error, not bad data.
